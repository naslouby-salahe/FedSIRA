# FedSIRA Pre-Experiment Audit Matrix

**Exact requirement count: 250**

**Scope:** pre-experiment verification only. This matrix was created from the authoritative FedSIRA roadmap and inspected against the current FedSIRA repository architecture/CLI snapshot. It does **not** record audit results, run scientific experiments, modify production code, or authorize a commit. Status and Finding/Action cells are intentionally blank until a later audit executes this matrix.

**Repository-specific basis inspected:** current public CLI (`doctor`, `preprocess`, `plan`, `smoke`, `run`, `status`, `report`); `FedSIRAApplication`; `configs/fedsira.yaml`; dataset, protocol, learning, experiment, evaluation/statistics, artifact, reporting, domain-type, and test subsystems; 19 registered experiment identities. Any later audit must inspect the then-current working tree again rather than assuming this snapshot is unchanged.

## 1. Purpose and scope

This file is an execution-ready verification plan for deciding whether FedSIRA is scientifically and technically ready to begin claim-bearing experiments. It intentionally stops before development/collapse/confirmatory/ablation/robustness/boundary/efficiency/generalization runs. A genuine lightweight `fedsira smoke` is allowed only as an invariant/wiring check after confirming that it cannot contaminate claim-bearing evidence. Real production preprocessing is mandatory before the gate can pass.

The later auditor must verify semantics rather than visual similarity to the roadmap tree. Real measured dataset facts may differ from pre-data expectations. Such differences are not defects when measured, documented, scientifically compatible, and classified as `JUSTIFIED_EMPIRICAL_DEVIATION`. Equivalent implementation structure may be `JUSTIFIED_ARCHITECTURE_DEVIATION` when the scientific contract and production wiring are preserved.

## 2. Authority hierarchy

1. **Scientifically authoritative:** formulas, algorithmic semantics, information restrictions, chronology/leakage rules, experiment designs and grids, methods/comparators, metrics, statistical units/tests/families, seed roles, collapse/claim criteria, and failure/downscope semantics.
2. **Empirically amendable:** measured client/cohort/row/class/campaign/time/support/resource properties and genuinely unavailable secondary conditions. Deviations require measured evidence and may not be manufactured to match an obsolete estimate.
3. **Implementation-flexible:** filenames, module boundaries, helper/class names, internal libraries, caching/parallelization implementation, and source-tree shape, provided scientific semantics, deterministic identity, artifact dependencies, and production reachability remain equivalent.

## 3. Status and severity definitions

Allowed Status values (use exactly one when executing the matrix): `PASS`, `FAIL`, `PARTIAL`, `MISSING`, `UNWIRED`, `DEAD_CODE_CANDIDATE`, `JUSTIFIED_EMPIRICAL_DEVIATION`, `JUSTIFIED_ARCHITECTURE_DEVIATION`, `BLOCKED_BY_PRE_EXPERIMENT_STATE`, `NOT_APPLICABLE`.

| Status | Meaning |
|---|---|
| `PASS` | Requirement is fully satisfied with recorded evidence. |
| `FAIL` | Implementation/evidence contradicts a required contract. |
| `PARTIAL` | Some required behavior/evidence exists but the obligation is incomplete. |
| `MISSING` | Mandatory implementation/evidence does not exist. |
| `UNWIRED` | Scientifically required implementation exists but is not reachable from the required production workflow. |
| `DEAD_CODE_CANDIDATE` | Unreachable code appears unnecessary only after required dynamic/framework/roadmap checks; it is not automatically dead. |
| `JUSTIFIED_EMPIRICAL_DEVIATION` | Real measured data/environment property differs from an expectation without violating the scientific contract. |
| `JUSTIFIED_ARCHITECTURE_DEVIATION` | Current architecture differs from historic roadmap structure but preserves semantics and wiring. |
| `BLOCKED_BY_PRE_EXPERIMENT_STATE` | Correctly unavailable because claim-bearing evidence must not exist yet; the implementation path itself is verified. |
| `NOT_APPLICABLE` | Requirement is demonstrably irrelevant to the resolved/current project condition, with reason recorded. |

| Severity | Meaning |
|---|---|
| `BLOCKER` | Must be resolved before any scientific experiment begins. |
| `MAJOR` | Material scientific/technical readiness issue; unresolved scientific MAJOR findings fail the gate. |
| `MINOR` | Quality/maintainability issue that does not by itself invalidate science, but still requires explicit resolution/disposition. |
